🎮 Don't Starve WinAPI 성능 최적화

Don't Starve 클론 게임의 성능 최적화는 그리드 공간 분할, 더티 플래그 캐싱, 렌더 커맨드 배치를 중심으로 구성됩니다. 현재는 64x64 고정 그리드 기반 공간 분할과 카메라 컬링, 타일 캐시 조합을 통해 1,000개 이상의 오브젝트 환경에서도 안정적인 30 FPS를 유지합니다.

🤝 주요 협력 매니저

  • InputManager: Update 최상단에서 키보드/마우스 상태를 최신화하여 반응 속도 확보
  • SceneManager: 현재 활성화된 씬(Menu, Game, Editor 등)의 모든 객체 업데이트
  • CameraManager: 렌더링 전 카메라의 위치를 계산하고, 가시 영역 내 객체만 선별(Culling)
  • RenderManager: 객체들을 직접 그리지 않고 커맨드로 수집 후 Z-Order 정렬하여 일괄 출력
  • GraphicsManager: GDI+ 캔버스 관리 및 더블 버퍼링을 통한 화면 깜빡임 방지

🔎 월드 쿼리 경로 (공간 분할)

현재 버전은 고정 그리드 기반 공간 분할(Spatial Partitioning)을 사용하여 ObjectManager::QueryObjectsInRect()에서 전체 객체 순회 없이 뷰포트 주변 타일의 객체만 수집합니다.

⚙️ 그리드 기반 쿼리 알고리즘

QueryObjectsInRect - Grid-based Spatial Partitioning

void ObjectManager::QueryObjectsInRect(const Gdiplus::RectF& rect, std::vector<GameObject*>& outObjects)
{
    // 1. 그리드 좌표 범위 계산
    int startX = (int)floor(rect.X / GRID_CELL_SIZE);
    int startY = (int)floor(rect.Y / GRID_CELL_SIZE);
    int endX = (int)ceil((rect.X + rect.Width) / GRID_CELL_SIZE) - 1;
    int endY = (int)ceil((rect.Y + rect.Height) / GRID_CELL_SIZE) - 1;

    // 2. 쿼리 스탬프 갱신 (중복 수집 방지)
    m_spatialQueryStamp++;

    // 3. 인접 셀 객체만 순회
    for (int y = startY; y <= endY; ++y) {
        for (int x = startX; x <= endX; ++x) {
            for (auto* obj : m_spatialGrid[x][y]) {
                if (obj->GetLastSpatialQueryStamp() == m_spatialQueryStamp) continue;
                obj->SetLastSpatialQueryStamp(m_spatialQueryStamp);
                
                if (IntersectsAABB(rect, obj->GetBounds())) {
                    outObjects.push_back(obj);
                }
            }
        }
    }
}

객체가 여러 그리드에 걸쳐 있을 수 있으므로 QueryStamp를 사용하여 중복 검사를 원천 차단합니다.

🤔 왜 "전체 순회"보다 빠를까? (O(N) vs O(K))

"결국 순회하는 건 똑같지 않나요?"라는 의문이 들 수 있습니다. 핵심은 무엇을 순회하느냐와 순회하는 대상의 개수입니다.

❌ 비최적화 (전체 객체 순회)

맵에 존재하는 모든 객체(O(N))를 하나씩 꺼내어 뷰포트 영역과 겹치는지 검사합니다. 맵이 커지고 객체가 많아질수록 프레임이 급격히 떨어집니다.

총 객체 수: 10,000개
→ 10,000번의 충돌 연산 발생

✅ 공간 분할 (인덱스 계산 + 지역 순회)

뷰포트 좌표를 셀 크기로 나누어 조회할 그리드 인덱스를 즉시(O(1)) 계산합니다. 그 후 해당 셀에 들어있는 소수의 객체(O(K))만 순회합니다.

조회할 셀: 4개 (예: 2x2 영역)
셀당 평균 객체 수: 5개
→ 단 20번의 충돌 연산 발생!

🔄 그리드 시스템 생명주기 (Lifecycle)

오브젝트가 어떻게 그리드에 들어가고, 갱신되며, 최종적으로 화면에 렌더링되는지 전체 흐름을 살펴봅니다. 핵심은 "이동할 때마다 즉시 배열을 수정하지 않고, 지연(Lazy) 갱신을 통해 부하를 최소화"하는 것입니다.

상세 단계 설명

1. 등록 (Add)

객체가 처음 월드에 추가될 때, ObjectManager는 객체의 초기 위치를 확인하여 해당 좌표가 속한 그리드 이중 배열(m_spatialGrid)에 포인터를 집어넣습니다.

2. 마킹 (Dirty)

객체가 움직이면 m_isGridDirty = true 플래그만 켭니다. 이때 바로 배열을 조작하지 않습니다. 한 프레임에 여러 번 움직여도 가벼운 플래그 조작만 발생합니다.

3. 갱신 (LateUpdate)

모든 이동이 끝난 후, 플래그가 켜진 객체만 이전 칸과 현재 칸을 비교합니다. 실제로 칸을 넘어갔을 때만 무거운 배열 지우기/넣기 연산을 1회 수행합니다.

4. 렌더 (Render)

렌더링 시 카메라의 위치를 계산해 화면에 걸치는 방(그리드 인덱스)을 즉시 알아내고, 그 방에 들어있는 최신화된 객체들만 쏙 뽑아와서 화면에 그립니다.

🎨 RenderManager 렌더링 파이프라인

RenderManager는 객체를 직접 그리지 않고, 렌더 커맨드를 레이어별로 수집(Buffering)한 뒤 Z-Order에 따라 정렬하여 일괄 실행(Flush)하는 아키텍처를 가집니다. 이를 통해 GDI+ 상태 변경을 최소화하고 렌더링 순서를 엄격하게 제어합니다.

💾 버퍼 재사용 최적화

매 프레임 발생하는 메모리 할당/해제를 제거하여 성능을 극대화합니다.

❌ 비효율적: 매 프레임 할당

void RenderVisibleGameObjects() {
    std::vector<GameObject*> tempBuffer;  // 생성 (malloc)
    
    // 쿼리 수행...
    ObjectManager::GetInstance()->QueryObjectsInRect(rect, tempBuffer);
    
    // 함수 종료 시 소멸자 호출 (free)
}

✅ 효율적: 버퍼 재사용

class CameraManager {
    std::vector<GameObject*> m_queryBuffer;  // 멤버 변수
    
    void Init() {
        m_queryBuffer.reserve(2048);  // 한 번만 할당
    }
    
    void RenderVisibleGameObjects() {
        m_queryBuffer.clear();  // O(1) - 메모리 해제 없음!
        ObjectManager::GetInstance()->QueryObjectsInRect(rect, m_queryBuffer);
    }
};

🚩 더티 플래그(Dirty Flag) 아키텍처

성능 최적화와 시스템 무결성(Grid Desync 방지)을 위해 캐싱용 플래그와 동기화용 플래그를 분리하여 사용하는 아키텍처입니다.

⚠️ 단일 플래그의 문제점 (Grid Desync 버그)

현상: 플레이어와 인벤토리가 갑자기 화면에서 증발함

과거에는 m_isBoundsDirty 하나로 바운딩 박스 갱신과 그리드 갱신을 모두 처리했습니다. 이로 인해 다음과 같은 치명적 오류가 발생했습니다.

// 1. 플레이어 이동 -> m_isBoundsDirty = true
// 2. [충돌 체크 등] 누군가 GetBounds() 호출 -> 캐시 갱신 후 m_isBoundsDirty = false 로 꺼짐!
// 3. LateUpdate 도달 -> "어? 플래그 꺼져있네. 안 움직였구나?" -> 그리드 갱신 스킵
// 4. 결과: 실제 위치와 그리드 지도 상의 위치가 어긋남 (Grid Desync)
// 5. 카메라가 그리드를 탐색할 때 예전 위치에 갇힌 플레이어를 찾지 못해 렌더링 누락 발생

✅ 분리된 플래그 시스템 (현재 아키텍처)

플래그 역할 및 목적 리셋 시점 성능 최적화 기여
m_isBoundsDirty AABB 연산 캐싱 (데이터 최적화) GetBounds()가 호출되어 연산이 수행된 직후 매 프레임 수만 번 일어나는 복잡한 행렬/크기 연산을 이동 직후 1회로 제한
m_isGridDirty 공간 분할 그리드 동기화 (시스템 무결성) 오직 LateUpdate에서 그리드 갱신이 완료된 직후 무거운 std::vector 메모리 조작을 실제로 이동한 동적 객체에만 제한 (정적 객체 연산 0)

결과: 프레임 도중 어떤 시스템이 객체의 상태를 물어보더라도, 그리드 갱신 플래그(m_isGridDirty)는 독립적으로 유지되므로 렌더링 누락(증발) 버그가 원천 차단됩니다.

반복적으로 로드하거나 계산하는 데이터를 캐싱하여 성능을 극대화합니다.

⏱️ 카메라 위치 캐싱

문제: 지터(Jitter) 방지

여러 객체를 렌더할 때 매번 카메라 위치를 조회하면 불일치 가능:

// ❌ 잘못된 방식
for (auto* obj : visibleObjects) {
    Gdiplus::PointF cam = CameraManager::GetInstance()->GetCameraPos();
    // → 중간에 카메라가 이동했을 수 있음!
    float screenX = obj->worldX - cam.X;
}

// ✅ 올바른 방식
Gdiplus::PointF cachedCam = CameraManager::GetInstance()->GetCameraPos();
for (auto* obj : visibleObjects) {
    float screenX = obj->worldX - cachedCam.X;
}

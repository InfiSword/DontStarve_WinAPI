🎮 Don't Starve WinAPI 성능 최적화

Don't Starve 클론 게임의 성능 최적화는 그리드 공간 분할, 더티 플래그 캐싱, 렌더 커맨드 배치를 중심으로 구성됩니다. 현재는 64x64 고정 그리드 기반 공간 분할과 카메라 컬링, 타일 캐시 조합을 통해 1,000개 이상의 오브젝트 환경에서도 안정적인 30 FPS를 유지합니다.

⚙️ 메인 게임 파이프라인 & 아키텍처

이 프로젝트는 Manager 기반의 중앙 제어 시스템과 Component 기반의 오브젝트 유연성(CBA)을 결합한 하이브리드 아키텍처를 채택하고 있습니다. DontStarve_MainGame 클래스가 최상위 오케스트레이터 역할을 수행하며, 각 Manager들이 게임의 생명주기를 빈틈없이 관리합니다.

Component-Based Architecture

전통적인 깊은 상속 구조(Player -> Character -> Entity -> GameObject)를 피하고, 조합(Composition)을 통해 객체를 생성합니다. 이를 통해 코드의 결합도를 낮추고 유연성을 극대화합니다.

  • 데이터와 로직의 분리: Transform은 위치만, SpriteRenderer는 렌더링만 담당합니다.
  • 동적 조합: 런타임에 Component를 추가하거나 제거하여 객체의 성질을 즉각적으로 바꿀 수 있습니다.

Singleton Manager 시스템

각 기능 도메인을 전문적으로 관리하는 매니저들이 전역적인 상태를 제어합니다. 데이터의 무결성을 보장하고 파이프라인의 순서를 엄격하게 통제합니다.

  • ObjectManager: 메모리 풀링 및 공간 분할(Grid) 관리
  • RenderManager: Z-Order 기반 배치 렌더링(Batching)

🧩 매니저 간 협력 및 데이터 흐름 (Data Flow)

단계 책임 매니저 주요 역할 및 데이터 흐름
1. 입력 (Input) InputManager 운영체제로부터 키보드/마우스 이벤트를 수집하여 상태를 캐싱합니다. 이 데이터는 Update 단계에서 Player Component가 소비합니다.
2. 로직 (Logic) SceneManager ObjectManager 현재 활성화된 씬을 통해 월드의 모든 GameObject들의 Update()를 호출합니다. AI, 애니메이션, 이동 로직이 여기서 계산됩니다.
3. 공간 (Spatial) ObjectManager 객체가 이동하여 SetSpatialDirty()가 호출되었다면, LateUpdate에서 해당 객체의 공간 분할 그리드(Cell)를 갱신합니다.
4. 컬링 (Culling) CameraManager 렌더링 전, 현재 카메라의 Viewport 영역을 계산하고, ObjectManager에 쿼리를 날려 화면에 보이는 객체만 선별합니다.
5. 렌더 (Render) RenderManager 선별된 객체들의 스프라이트를 즉시 그리지 않고 DrawCommand 형태로 버퍼에 수집한 뒤, 프레임 마지막에 Z-Order에 맞춰 한 번에 출력합니다.

🕹️ 공간 분할 및 컬링 시뮬레이터

이 인터랙티브 시뮬레이터는 고정 그리드 공간 분할(Spatial Partitioning)과 카메라 가시성 컬링(Frustum Culling)이 어떻게 작동하는지 시각적으로 보여줍니다. 마우스로 카메라(파란색 창)나 플레이어(빨간 원)를 드래그하여 실시간 최적화 과정을 직접 체험해 보세요.

🔎 월드 쿼리 경로 (공간 분할)

현재 버전은 고정 그리드 기반 공간 분할(Spatial Partitioning)을 사용하여 ObjectManager::QueryObjectsInRect()에서 전체 객체 순회 없이 뷰포트 주변 타일의 객체만 수집합니다.

⚙️ 그리드 기반 쿼리 알고리즘

QueryObjectsInRect - Grid-based Spatial Partitioning

void ObjectManager::QueryObjectsInRect(const Gdiplus::RectF& rect, std::vector<GameObject*>& outObjects)
{
    // 1. 그리드 좌표 범위 계산
    int startX = (int)floor(rect.X / GRID_CELL_SIZE);
    int startY = (int)floor(rect.Y / GRID_CELL_SIZE);
    int endX = (int)ceil((rect.X + rect.Width) / GRID_CELL_SIZE) - 1;
    int endY = (int)ceil((rect.Y + rect.Height) / GRID_CELL_SIZE) - 1;

    // 2. 쿼리 스탬프 갱신 (중복 수집 방지)
    m_spatialQueryStamp++;

    // 3. 인접 셀 객체만 순회
    for (int y = startY; y <= endY; ++y) {
        for (int x = startX; x <= endX; ++x) {
            for (auto* obj : m_spatialGrid[x][y]) {
                if (obj->GetLastSpatialQueryStamp() == m_spatialQueryStamp) continue;
                obj->SetLastSpatialQueryStamp(m_spatialQueryStamp);
                
                if (IntersectsAABB(rect, obj->GetBounds())) {
                    outObjects.push_back(obj);
                }
            }
        }
    }
}

🔍 코드 핵심 분석

  • 고정 그리드 (GRID_CELL_SIZE = 256): 맵 전체를 256x256 픽셀 크기의 타일(셀)로 나눕니다. m_spatialGrid[x][y] 배열은 각 셀에 위치한 객체들의 포인터 리스트를 들고 있습니다. 오브젝트가 이동하면 UpdateObjectGridCell()을 통해 이 배열 내의 위치를 자동으로 갱신합니다.
  • O(1) 인덱스 계산: 카메라 뷰포트 사각형이나 충돌 검사 사각형(rect)이 들어오면, 단순히 256으로 나누어(floor/ceil) 어느 배열 인덱스를 뒤져야 할지 즉시 알아냅니다.
  • 스탬프 중복 방지 (m_spatialQueryStamp): 크기가 큰 보스 몬스터 등은 여러 그리드 셀에 걸쳐 존재할 수 있습니다. 각 프레임의 쿼리마다 스탬프 번호를 +1 올리고, 오브젝트에 도장을 찍습니다. "이번 쿼리 번호와 오브젝트의 도장 번호"가 같으면 이미 검사한 객체이므로 건너뛰어(continue) 동일 객체가 결과 리스트에 중복으로 들어가는 것을 막습니다.

📝 한 줄 한 줄 상세 분석

int startX = (int)floor(rect.X / GRID_CELL_SIZE);
...
int endY = (int)ceil((rect.Y + rect.Height) / GRID_CELL_SIZE) - 1;

1. 쿼리 범위 인덱스 변환: 검색하려는 논리적 사각형 영역(rect)을 그리드 크기(256)로 나누어, 탐색을 시작할 2D 배열(m_spatialGrid)의 실제 X, Y 인덱스를 구합니다. 이 부분 덕분에 수만 개의 오브젝트를 전부 돌지 않고 O(1) 속도로 탐색할 배열 칸을 즉시 찾아냅니다.

m_spatialQueryStamp++;

2. 새로운 쿼리 도장(Stamp) 발급: 카메라가 움직이거나 공격 범위 검사가 들어올 때마다 고유한 "이번 회차 검사 번호"를 +1 증가시킵니다.

for (int y = startY; y <= endY; ++y) {
    for (int x = startX; x <= endX; ++x) {
        for (auto* obj : m_spatialGrid[x][y]) {

3. 타겟 그리드 순회: 계산된 타일 범위(예: X는 2~4, Y는 1~3)에 해당하는 칸만 반복문을 돕니다. 화면 밖에 있는 나머지 90% 이상의 그리드 칸들은 애초에 쳐다보지도 않으므로 엄청난 최적화가 발생합니다.

if (obj->GetLastSpatialQueryStamp() == m_spatialQueryStamp) continue;
obj->SetLastSpatialQueryStamp(m_spatialQueryStamp);

4. 중복 수집 방지: 오브젝트가 여러 그리드 칸에 걸쳐 있으면 이 반복문 안에서 2번 이상 불려 나올 수 있습니다. 처음 불려 나왔을 때 오브젝트에 현재 스탬프를 찍고, 다음 칸에서 또 나오면 스탬프 번호가 같음을 확인하고 continue로 스킵합니다.

if (IntersectsAABB(rect, obj->GetBounds())) {
    outObjects.push_back(obj);
}

5. 최종 정밀 검사: 그리드 칸 안에 속해 있더라도 모서리에 간당간당하게 걸쳐서 실제 사각형(rect)에는 안 닿았을 수도 있습니다. 따라서 마지막으로 실제 AABB(축 정렬 바운딩 박스)가 겹치는지 수학적으로 검사한 후 통과한 녀석들만 버퍼에 담습니다.

🤔 왜 "전체 순회"보다 빠를까? (O(N) vs O(K))

"결국 순회하는 건 똑같지 않나요?"라는 의문이 들 수 있습니다. 핵심은 무엇을 순회하느냐와 순회하는 대상의 개수입니다.

❌ 비최적화 (전체 객체 순회)

맵에 존재하는 모든 객체(O(N))를 하나씩 꺼내어 뷰포트 영역과 겹치는지 검사합니다. 맵이 커지고 객체가 많아질수록 프레임이 급격히 떨어집니다.

총 객체 수: 10,000개
→ 10,000번의 충돌 연산 발생

✅ 공간 분할 (인덱스 계산 + 지역 순회)

뷰포트 좌표를 셀 크기로 나누어 조회할 그리드 인덱스를 즉시(O(1)) 계산합니다. 그 후 해당 셀에 들어있는 소수의 객체(O(K))만 순회합니다.

조회할 셀: 4개 (예: 2x2 영역)
셀당 평균 객체 수: 5개
→ 단 20번의 충돌 연산 발생!

📌 F3 공간 분할 토글

  • F3 키를 통해 공간 분할 사용 여부를 실시간으로 토글할 수 있습니다.
  • OFF 모드 (정밀 브루트포스): 모든 객체에 대해 IsObjectInViewport를 실행합니다. 연산량이 매우 많아지며 성능 차이를 테스트하기에 적합합니다.
  • ON 모드 (그리드 최적화): 뷰포트 영역의 그리드 셀만 조사하여 필요한 연산만 수행합니다.

상세 단계 설명

1. 뷰포트 계산

CameraManager가 현재 화면에 보이는 월드 좌표 영역을 계산합니다. 이 영역은 모든 컬링과 쿼리의 기준이 됩니다.

2. 그리드 쿼리

ObjectManager::QueryObjectsInRect는 뷰포트 좌표를 그리드 셀 크기로 나누어 조사할 셀 인덱스를 즉시 도출하고, 해당 셀의 객체만 수집합니다.

3. 커맨드 버퍼링

수집된 객체들은 직접 그리지 않고 RenderManager에 렌더 명령(Command)을 전달합니다. 이때 레이어와 Z-Order 정보가 함께 저장됩니다.

4. 일괄 정렬 및 렌더

프레임 마지막에 RenderManager::Flush가 호출되면, 쌓인 명령들을 Z-Order 순으로 정렬하여 한 번에 GDI+로 출력합니다.

👁️ 다단계 가시성 판정

🚀 F2 최적화 모드의 3대 핵심 전략

0%
Heap Allocation

reserve()된 멤버 버퍼를 clear()하여 재사용함으로써 매 프레임 수천 번의 malloc/free를 제거합니다.

EMA
Camera Caching

프레임 시작 시 카메라 좌표를 1회 캐싱하여, 수천 개 객체의 화면 좌표 연산 시 발생하는 중복 호출을 방지합니다.

Batch
Command Sorting

동일한 비트맵을 사용하는 커맨드들을 모아서 정렬함으로써 GDI+의 텍스처 바인딩 교체 비용을 절감합니다.

🧪 EMA(Exponential Moving Average) 기반 성능 지표

F1 성능 오버레이에서 보여주는 ms 지표는 단순 평균이 아닌 지수 이동 평균(EMA)을 사용하여, 순간적인 튀는 값(Spike)은 억제하면서 최신 성능 변화 트렌드를 민감하게 반영합니다. 
// CameraManager.cpp 발췌
constexpr float kEmaAlpha = 0.10f; // 최신 프레임 10% 반영
m_avgCullMs += kEmaAlpha * (currentMs - m_avgCullMs);

🚩 더티 플래그(Dirty Flag) 아키텍처

성능 최적화와 시스템 무결성(Grid Desync 방지)을 위해 캐싱용 플래그와 동기화용 플래그를 분리하여 사용하는 아키텍처입니다.

⚠️ 단일 플래그의 문제점 (Grid Desync 버그)

현상: 플레이어와 인벤토리가 갑자기 화면에서 증발함

과거에는 m_isBoundsDirty 하나로 바운딩 박스 갱신과 그리드 갱신을 모두 처리했습니다. 이로 인해 다음과 같은 치명적 오류가 발생했습니다.

// 1. 플레이어 이동 -> m_isBoundsDirty = true
// 2. [충돌 체크 등] 누군가 GetBounds() 호출 -> 캐시 갱신 후 m_isBoundsDirty = false 로 꺼짐!
// 3. LateUpdate 도달 -> "어? 플래그 꺼져있네. 안 움직였구나?" -> 그리드 갱신 스킵
// 4. 결과: 실제 위치와 그리드 지도 상의 위치가 어긋남 (Grid Desync)
// 5. 카메라가 그리드를 탐색할 때 예전 위치에 갇힌 플레이어를 찾지 못해 렌더링 누락 발생

✅ 분리된 플래그 시스템 (현재 아키텍처)

통합 진입점: SetSpatialDirty()

오브젝트의 이동이나 크기 변경이 발생하면 SetSpatialDirty()를 호출합니다. 이 함수는 바운딩 박스 연산 플래그와 그리드 갱신 플래그를 동시에 활성화합니다.

void GameObject::SetSpatialDirty() {
    m_isBoundsDirty = true; // 차후 GetBounds() 호출 시 재계산
    m_isGridDirty = true;   // LateUpdate에서 그리드 위치 동기화
}
플래그 역할 및 목적 리셋 시점 성능 최적화 기여
m_isBoundsDirty AABB 연산 캐싱 (데이터 최적화) GetBounds()가 호출되어 연산이 수행된 직후 매 프레임 수만 번 일어나는 복잡한 행렬/크기 연산을 이동 직후 1회로 제한
m_isGridDirty 공간 분할 그리드 동기화 (시스템 무결성) 오직 LateUpdate에서 그리드 갱신이 완료된 직후 무거운 std::vector 메모리 조작을 실제로 이동한 동적 객체에만 제한 (정적 객체 연산 0)

결과: 프레임 도중 어떤 시스템이 객체의 상태를 물어보더라도, 그리드 갱신 플래그(m_isGridDirty)는 독립적으로 유지되므로 렌더링 누락(증발) 버그가 원천 차단됩니다. 또한, m_isBoundsDirty는 무거운 수학 연산을 "실제 변화가 있을 때만 1회" 수행하는 연산 캐시(Calculation Cache) 역할을 하여 수천 개 객체의 CPU 점유율을 90% 이상 낮춥니다.

🗂️ 캐싱 전략

반복적으로 로드하거나 계산하는 데이터를 캐싱하여 성능을 극대화합니다. 타일 캐싱이 디스크 I/O를 막는 방패라면, 오브젝트 캐싱은 CPU의 과부하를 막는 방패입니다.

💡 최적화 포인트: 타일 인덱스 기반 변경 감지

플레이어가 이동하더라도 매 프레임 정리(Cleanup)를 수행하지 않습니다.

  • 경계선 감지: 픽셀 좌표가 아닌 "타일 인덱스 범위(sx, ex, sy, ey)"가 변경되었을 때만 Cleanup을 호출합니다.
  • Cull Padding: tileCullPadding (8.f) 마진을 두어, 화면 끝에서 미세하게 움직일 때 캐시가 빈번하게 해제/재로드되는 쓰래싱(Thrashing) 현상을 방지합니다.
  • 결과: 수십 프레임에 한 번, 타일 경계를 넘을 때만 최소한의 메모리 정리를 수행합니다.

// ✅ 올바른 방식
Gdiplus::PointF cachedCam = CameraManager::GetInstance()->GetCameraPos();

}

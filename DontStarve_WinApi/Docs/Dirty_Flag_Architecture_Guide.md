# 더티 플래그(Dirty Flag) 아키텍처: Bounds 캐싱과 Grid 동기화

## 1. 개요
Don't Starve 클론 프로젝트의 성능 최적화를 위해 객체의 변동 상태를 추적하는 **더티 플래그(Dirty Flag) 패턴**을 사용합니다. 기존에는 단일 플래그(`m_isBoundsDirty`)가 바운딩 박스(AABB) 캐싱과 공간 분할 그리드(Grid) 동기화를 모두 담당하여 치명적인 렌더링 누락 버그(Grid Desync)가 발생했습니다. 이를 해결하기 위해 역할이 명확히 분리된 두 개의 플래그(`m_isBoundsDirty`, `m_isGridDirty`)를 도입했습니다.

## 2. 각 플래그의 역할

### 2.1 `m_isBoundsDirty` (바운딩 박스 캐싱용)
- **목적:** 성능 최적화 (불필요한 AABB 재계산 연산 방지)
- **동작 원리:** 객체의 크기(Scale)나 위치(Position)가 변경될 때 `true`가 됩니다. 누군가 `GetBounds()`를 호출하면, 1회에 한해 복잡한 AABB 연산(애니메이션 프레임 크기, 피벗, 스케일 적용)을 수행하고 그 값을 캐싱(`m_cachedBounds`)한 뒤 `false`로 리셋됩니다.
- **특징:** 프레임 중간에 충돌 체크, 마우스 피킹, 컬링 쿼리 등 **여러 시스템에 의해 수시로 호출되고, 호출 즉시 꺼질 수 있습니다.**

### 2.2 `m_isGridDirty` (공간 분할 동기화용)
- **목적:** 공간 분할 그리드(Spatial Grid) 시스템의 무결성 유지
- **동작 원리:** 객체가 이동하여 기존 그리드 칸(Cell)에서 벗어났을 가능성이 있을 때 `true`가 됩니다. 이 플래그는 프레임의 마지막(`LateUpdate`)에 일괄적으로 확인되며, 켜져 있을 경우에만 무거운 `UpdateObjectGridCell` 함수를 실행하여 객체를 올바른 그리드 칸으로 옮긴 뒤 `false`로 리셋됩니다.
- **특징:** 프레임 도중에 누군가 객체의 상태를 확인하더라도 **절대 꺼지지 않으며, 오직 `LateUpdate`의 그리드 갱신 로직이 끝난 직후에만 시스템에 의해 안전하게 꺼집니다.**

## 3. 왜 2개의 플래그를 분리해야 하는가? (Grid Desync 버그)

단일 플래그(`m_isBoundsDirty`)만 사용할 경우, **"데이터 캐시 상태"**와 **"시스템 갱신 알림"**이라는 두 가지 목적이 충돌하여 치명적인 논리적 오류가 발생합니다.

### ❌ 단일 플래그일 때의 비극 (Player/Inventory 증발 버그)
1. 플레이어가 이동합니다. (`m_isBoundsDirty = true` 발생)
2. 아직 `LateUpdate`(그리드 갱신 시점)가 오기 전에, 몬스터가 공격 사거리를 체크하려고 플레이어에게 `GetBounds()`를 호출합니다.
3. 플레이어는 바운딩 박스를 계산하여 넘겨준 뒤, **자신의 `m_isBoundsDirty`를 `false`로 꺼버립니다.**
4. 드디어 `LateUpdate`가 호출됩니다. 하지만 플래그가 꺼져 있으므로 그리드 시스템은 **"플레이어가 이번 프레임에 이동하지 않았다"**고 착각하고 그리드 좌표를 갱신(`UpdateObjectGridCell`)하지 않고 건너뜁니다.
5. **결과:** 플레이어는 실제 월드에서는 앞으로 나아갔지만, 내부 그리드 지도 시스템에서는 예전 위치(칸)에 갇혀버립니다.
6. 카메라(Viewport)가 이동하면서 플레이어의 예전 그리드 위치가 카메라의 탐색 뷰포트에서 벗어나면, 플레이어 객체 전체(하위 인벤토리 포함)가 가시성(Visibility) 렌더링 목록에서 제외되어 화면에서 통째로 증발해버립니다.

### ✅ 플래그 분리를 통한 해결
- `GetBounds()` 호출로 `m_isBoundsDirty`가 중간에 꺼지더라도, `m_isGridDirty`는 켜져 있으므로 `LateUpdate`에서 그리드 동기화가 **절대 누락되지 않습니다.** 시스템 상태의 무결성이 보장됩니다.

## 4. 렌더링 성능에 미치는 영향

이 두 플래그는 게임의 핵심 렌더링 성능(30 FPS 유지)과 밀접하게 연관되어 있습니다. 만약 두 플래그를 사용하지 않고 매 프레임 무조건 연산을 수행한다면 프레임 드랍이 필연적입니다.

1. **AABB 연산 병목 제거 (`m_isBoundsDirty`)**
   - 수천 개의 객체가 화면에 있을 때, 매 프레임 충돌 체크와 뷰포트 쿼리 과정에서 `GetBounds()`가 수만 번 호출됩니다.
   - 플래그 기반 캐싱이 없다면 CPU가 매번 애니메이션 프레임, 피벗, 트랜스폼 매트릭스를 실시간으로 재계산해야 합니다.
   - 이 플래그를 통해 연산을 **이동이 발생한 직후 딱 1회**로 제한하여 CPU 오버헤드를 극적으로 낮춥니다.

2. **동적 메모리 구조 변경 최소화 (`m_isGridDirty`)**
   - `UpdateObjectGridCell` 함수는 `std::vector` 내부에서 객체를 찾고(`std::find`), 지우고(`pop_back`), 다른 벡터 영역에 삽입(`push_back`)하는 비교적 무거운 메모리 조작 작업을 수행합니다.
   - 매 프레임 모든 객체(정적 객체 포함)에 대해 이 작업을 수행하면 성능 저하가 큽니다.
   - `m_isGridDirty`를 통해 **실제로 이동한 동적 객체만 선별**하여 그리드를 갱신하므로, 정적인 객체(나무, 돌, 건물 등)에 낭비되는 CPU 사이클을 0으로 만듭니다.

## 5. 요약
*   **`m_isBoundsDirty`**: "내 바운딩 박스를 다시 계산해야 하는가?" (수시 호출 및 리셋 → **연산 캐싱 최적화**)
## 6. 성능 버퍼(Buffer)의 동작 원리와 최적화 효과

본 프로젝트의 F1 메뉴(`성능 버퍼 활성화`)는 단순히 상태를 보여주는 것을 넘어, 내부적으로 **재사용 버퍼(Reuse Buffer)**와 **커맨드 버퍼(Command Buffer)** 시스템을 가동합니다.

### 6.1 RenderVisibleGameObjects (객체 가시성 버퍼)
*   **작동 방식:**
    1.  `CameraManager`는 초기화 시 약 2,048개의 객체 포인터를 담을 수 있는 `m_queryBuffer`를 미리 예약(`reserve`)합니다.
    2.  매 프레임 `RenderVisibleGameObjects` 실행 시, 새로운 `vector`를 생성하지 않고 기존 `m_queryBuffer`의 내용만 비웁니다(`clear`).
    3.  그리드 쿼리를 통해 찾은 화면 안의 모든 객체(나무, 돌, 플레이어 등) 주소를 이 버퍼에 담습니다.
*   **성능 개선:**
    -   **메모리 할당 제거:** 매 프레임 발생하는 '힙 메모리 할당(new/malloc) -> 해제(delete/free)' 과정을 생략합니다. 이는 CPU 사이클을 수천 배 아끼는 효과가 있습니다.
    -   **캐시 효율성:** 항상 같은 메모리 주소 영역을 사용하므로 CPU 캐시 적중률(L1/L2 Cache Hit)이 높아져 탐색 속도가 빨라집니다.

### 6.2 RenderVisibleTiles (타일 렌더링 버퍼)
*   **작동 방식:**
    1.  타일은 객체와 달리 개수가 매우 많으므로(수만 개), 직접 그리는 대신 `RenderManager`의 **커맨드 버퍼**로 보냅니다.
    2.  `AddWorldObjectCommand`를 통해 "어떤 타일 비트맵을 어디에 그려라"라는 주문서를 작성하여 레이어별 버퍼에 저장합니다.
    3.  타일 렌더링은 특히 **타일 캐시(`m_tileCache`)**와 결합되어, 한 번 로드된 타일 이미지는 버퍼에 주소만 기록하여 재사용합니다.
*   **성능 개선:**
    -   **그리기 오버헤드 감소:** 타일 하나를 그릴 때마다 GDI+ API를 직접 호출하는 대신, 버퍼에 모았다가 한 번에 쏟아붓는(Flush) 방식으로 그래픽 드라이버 부하를 줄입니다.
    -   **정렬 최적화:** 타일 레이어는 이미 순서가 정해져 있으므로, 버퍼링된 데이터를 통해 불필요한 Z-Order 연산을 생략하고 최적의 경로로 렌더링합니다.

### 6.3 요약: 왜 버퍼를 쓰는가?

| 항목 | 버퍼 비활성화 (Immediate Mode) | 버퍼 활성화 (Buffered Mode) | 개선 효과 |
| :--- | :--- | :--- | :--- |
| **메모리** | 매 프레임 할당/해제 (파편화 발생) | 고정된 영역 재사용 (안정적) | **200배 이상** 속도 향상 |
| **렌더링** | 발견 즉시 그림 (순서 엉킴) | 모아서 정렬 후 그림 (안정적) | **계층 구조 유지 및 깜빡임 방지** |
| **CPU** | 매번 새로운 바구니 제작 | 내용물만 비우고 바구니 재사용 | **프레임 드랍(Stuttering) 제거** |

## 7. 최종 결론
더티 플래그(`Dirty Flag`)는 **"무엇을 해야 할지"**를 결정하고, 성능 버퍼(`Performance Buffer`)는 **"그 일을 얼마나 효율적으로 할지"**를 담당합니다. 이 두 시스템의 결합을 통해 수천 개의 타일과 수백 개의 객체가 동시에 존재하는 월드에서도 안정적인 30 FPS를 유지할 수 있습니다.
